# To PRD

Use this when the idea is understood and you need a durable spec.

## Rules

- Synthesize what is already known; do not restart the interview.
- Read the repo docs and codebase context first if there is a target project.
- Write the PRD in terms of problem, solution, user stories, decisions, tests, out of scope, and open questions.
- Keep implementation details high-level and avoid file paths unless they are decision-critical.
- If the target system uses Linear, make the brief ready to paste there.
